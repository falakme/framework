# AGENTS.md: how to build apps with Falak

This file is for AI agents that create or change a Falak app. Read it before you touch
an app's YAML. The full rules are in [specifications/SCHEMA_SPECIFICATION.md](specifications/SCHEMA_SPECIFICATION.md),
[specifications/AUTHORIZATION_SPECIFICATION.md](specifications/AUTHORIZATION_SPECIFICATION.md)
and [specifications/API_SPECIFICATION.md](specifications/API_SPECIFICATION.md). When this
file and a specification disagree, the specification wins.

## 1. What Falak is

You describe data, access rules and commands in YAML. The `falak` CLI compiles that into
an API with authorization enforced on every request. You never write the server, the
routes or the SQL. You write files, run `falak check`, and fix what it reports.

## 2. Tools

Install the CLI from a clone of the repository (the crates.io build works for apps, but
`falak deploy` needs the clone):

```bash
cargo install --path crates/falak-cli --locked
falak --version
```

| Command | Use it to |
| :-- | :-- |
| `falak init <dir> --name <app>` | Create an app skeleton. Do this once per app. |
| `falak check [dir]` | Validate the app. Run it after every change; fix every error. |
| `falak build [dir]` | Compile and write `falak.lock` and `.falak/ir.json`. |
| `falak dev [dir]` | Serve on `http://127.0.0.1:8787` and reload on each file change. |
| `falak serve [dir]` | Serve without watching files. |
| `falak openapi [dir]` | Write `.falak/openapi.json`. |
| `falak sync [dir] --out <file>` | Write a typed TypeScript client. |
| `falak policy explain [dir] --entity <e> --action <a> --subject <id> --role <r>` | Show why a request is allowed or denied, with the matching rules. Use it to test policies. |
| `falak migrate plan` / `falak migrate apply` | Show or run the changes needed to bring a database to this version. |
| `falak doctor [dir]` | Check the machine, the port and the app. |

`falak check` prints the file, line and column of each problem. Treat its message as the
fix instruction; it often suggests the correct name or type.

## 3. Files in an app

```text
my-app/
├── app.yaml                 # exactly one: name, version, tenancy, drivers
├── entities/<name>.yaml     # one entity per file
├── policies/<name>.yaml     # one policy per entity, same name
├── commands/<name>.yaml     # one command per file
├── events/<name>.yaml       # optional: event contracts (cross-app)
├── workflows/<name>.yaml    # optional: sagas
├── migrations/              # generated by falak, do not edit
├── falak.lock               # generated by falak build; commit it
└── .falak/                  # runtime files (database, keys); never commit
```

Rules:

* The file name, without `.yaml`, must equal the `entity`, `command` or `event` it declares.
* Every file starts with `schema_version: 1`. Unknown keys are errors.
* Do not use YAML anchors, aliases, merge keys (`<<`), explicit tags or several documents
  in one file. Quote any string that looks like another type (`"1.0"`, `"null"`, `"0x10"`).
  `yes`, `no`, `on` and `off` are plain strings.
* Do not edit `falak.lock`, `.falak/` or `migrations/` by hand. Change the YAML and rebuild.
* Keep `jobs/` empty. It is reserved.

## 4. Naming and limits

* Entity, field, command, role and rule names match `^[a-z][a-z0-9_]{0,62}$`.
* App names match `^[a-z][a-z0-9_-]{1,39}$`.
* Do not name an entity or field with a SQL reserved word, or with a built-in field
  (`id`, `version`, `created_at`, `updated_at`, `tenant_id`, `deleted_at`).
* Limits: 200 entities, 100 fields per entity, 100 commands per app.

## 5. The app file

```yaml
schema_version: 1
name: notebook
version: 0.1.0
description: A personal notebook. Each person sees only their own notes.
tenancy: none            # none | row | database
trust_tier: standard     # standard | sensitive | high_assurance
drivers: [sqlite, postgres, d1]
```

`drivers` lists the databases the app must run on. The build fails if the app needs a
feature one of them lacks, so list only the targets you will really use.

## 6. Entities

```yaml
schema_version: 1
entity: note
owner: owner_id
fields:
  title: { type: text, required: true, max_length: 200 }
  body: { type: text, max_length: 20000 }
  archived: { type: bool, default: false }
  notebook_id: { type: uuid, required: true, indexed: true, references: notebook.id }
  owner_id: { type: uuid, required: true, indexed: true }
relations:
  notebook: { kind: belongs_to, entity: notebook, field: notebook_id }
admin:
  label: Notes
  list_columns: [title, archived]
  search_fields: [title]
lifecycle:
  soft_delete: true
  erasable: true
```

Field types: `uuid`, `int64`, `decimal_minor`, `text`, `bool`, `timestamptz`, `bytes`, `json`.

* There is **no float type**. Use `decimal_minor` for money (an integer count of cents) and
  `int64` for counts.
* `text` needs `max_length` above 4096 if you go higher; the limit is 1,048,576.
* Field options: `required`, `unique`, `indexed`, `default` (a literal, or `now` for
  `timestamptz`, `uuid` for `uuid`), `min` and `max` (for `int64` and `decimal_minor`),
  `pii`, `encrypted`, `references` (for `uuid`, written `entity.field`).
* `encrypted` fields cannot be filtered, sorted, indexed or made unique. `json` fields
  cannot be filtered.
* Every entity gets `id`, `version`, `created_at` and `updated_at` automatically. Never
  declare them.
* `owner: <field>` names a `uuid` field that holds the owner's user id. The server sets it
  from the caller on create, and it cannot change afterwards. Any policy that uses
  `owner: true` requires it.
* A `belongs_to` relation must have a matching `has_many` on the other entity if you
  declare the reverse side. Both sides must agree.

## 7. Policies: who may do what

```yaml
schema_version: 1
entity: note
rules:
  - id: owner_full_access
    actions: [read, create, update, delete]
    allow: { owner: true }
  - id: admin_read
    actions: [read]
    allow: { role: admin }
```

* **Default deny.** An entity with no policy file allows nothing. Every entity needs a
  policy before it is useful.
* **Rules add up.** An action is allowed if any rule listing it is satisfied. There is no
  deny rule. Use the smallest set of actions you need.
* `allow` has exactly one condition: `owner: true`, `role: <name>` or `authenticated: true`.
* Actions: `read` (get and list), `create`, `update`, `delete`.
* A caller who cannot read a row does not see it in lists, and a direct GET returns `404`,
  never `403`. This is intentional.
* Do not give a role access by default. Roles come from the verified token; check the
  role names against the auth setup before you use them.
* After you change a policy, check it with `falak policy explain`.

## 8. Commands

Commands are named mutations. Use them for changes that are more than a plain create,
update or delete.

```yaml
schema_version: 1
command: archive_note
entity: note
kind: update
input:
  id: { type: uuid, required: true }
target: id
set:
  archived: true
idempotent: true
```

* `kind: create | update | delete` is declarative. `update` and `delete` need a `target`
  naming a `uuid` input field that holds the row id. `delete` must not have `set`.
  `update` must have `set`.
* `set` values are literals or `$input.<name>`.
* `kind: custom` calls a Rust handler registered in the runtime. Only add one if the
  framework has that handler; you cannot add it from an app's YAML alone.
* The caller is authorised for the action the command performs: an `update` command needs
  `update` permission on that entity. Commands run as the caller.
* Input fields are validated before anything runs. Unknown inputs are rejected.
* `idempotent: true` makes the client send an `Idempotency-Key` header. Use it for any
  command a retry could repeat.
* Over HTTP, a command is `POST /v1/<entities>/<id>/<command_name>`, for example
  `POST /v1/notes/<id>/archive_note`. The segment must equal the command's `command` name
  exactly. Check `.falak/openapi.json` for the exact path.

## 9. Calling the API

Base URL in development: `http://127.0.0.1:8787`.

| Request | Meaning |
| :-- | :-- |
| `POST /v1/auth/signup` and `POST /v1/auth/login` | Create an account and get `access_token` (15 minutes) and `refresh_token`. |
| `POST /v1/auth/refresh` | Trade a refresh token for a new pair. Refresh tokens rotate, and reuse revokes the session. |
| `GET /v1/<entities>` | List. Supports `filter[field]=value`, `sort=-created_at,id`, `page[size]`, `page[after]`, `fields[entity]=a,b` and `include=relation`. |
| `POST /v1/<entities>` | Create. Send `Idempotency-Key` for retries. |
| `GET /v1/<entities>/<id>` | Get one. Returns `ETag`. |
| `PATCH /v1/<entities>/<id>` | Update. Send `If-Match: <etag>` to avoid overwriting someone else's change; a stale tag returns `412`. |
| `DELETE /v1/<entities>/<id>` | Delete (soft if `lifecycle.soft_delete`). |
| `GET /openapi.json` | The current API description. |

Send the access token as `Authorization: Bearer <token>`. Errors use RFC 7807 problem
JSON. A `401` on every request usually means an expired access token: refresh it.

Use the generated client (`falak sync`) in TypeScript apps. It adds an idempotency key to
each write automatically; pass `ifMatch` on updates to get optimistic locking.

## 10. Working loop

1. Read the request and find the entities it touches. Check whether `falak check` already
   passes.
2. Edit the YAML: the entity, its policy, then any command.
3. Run `falak check`. Fix every error before going further.
4. Run `falak build`, then `falak policy explain` for each new rule.
5. Run `falak dev` and test the endpoints with the access rules in mind: one signed-in
   person, a second person who must see nothing, and an unauthenticated call.
6. Commit the YAML and `falak.lock`. Do not commit `.falak/`.

## 11. Known limits to design around

* Changes to an existing entity do not add columns to an existing table yet. In development,
  delete `.falak/data.db` and restart. Use `falak migrate plan` and `falak migrate apply`
  for real databases.
* Stage 1 policies are ownership, roles and `authenticated` only. Attribute conditions and
  relationship rules are not frozen yet.
* Tier 3 apps (`trust_tier: high_assurance` with online checks) are refused by Falak Office.
* On Cloudflare Workers, `/v1/_files` answers `501`.

## 12. Things you must not do

* Do not write real passwords, API keys or tokens into YAML, examples or commits.
  `.falak/keys.json` holds the signing key; it stays on the machine.
* Do not weaken a policy to make a test pass. Fix the test's identity or role instead.
* Do not add `float` fields for money or measurements.
* Do not edit `falak.lock` or generated migrations by hand.
* Do not expose `falak dev` to the network. It listens on loopback only. For anything
  else, use `falak serve` with `FALAK_HOST` behind a TLS proxy.
* Do not put personal data in URLs or query strings.
