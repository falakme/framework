**Status:** Draft v1 (Phase 0 / Milestone M0).  
**Authors:** Dev2 (Native Runtime & Data Lead), with Cloudflare D1 limits contributed by Dev3 (T0.7).  
**Target Gate:** Frozen at Milestone M2 exit.

## 1. Overview & Principles

Falak is a metadata-driven application framework designed to run identically across diverse database engines without compromising safety, predictability, or performance.

Rather than presenting an abstraction that lowest-common-denominator reduces database functionality or hides engine differences behind fragile emulation layers, Falak enforces **strict capability profiling**:
1. **Explicit Capability Profiles:** Every storage driver statically declares its supported transaction semantics, concurrency features, SQL extensions, and numeric execution limits.
2. **Compile-Time Validation:** The Falak compiler (`falak build`) cross-references an application's compiled AST requirements against the target driver's capability profile. If an application utilizes features (e.g. interactive transactions or native row-level security) unsupported by the chosen driver, the build fails with an actionable diagnostic.
3. **Parameterized Statements Only:** Drivers execute only parameterized statements generated by the compiler or registered in Level-2 restricted SQL definitions. Callers never format or concatenate raw SQL strings.
4. **Context-Injected Isolation:** Every query and transaction carries a `RequestContext` containing the authenticated `Principal`. Drivers use this context to enforce tenancy and isolation at the lowest possible layer (such as PostgreSQL Row-Level Security session variables or SQLite parameterized tenant predicates).

## 2. Provider Traits

The storage contract is defined in `crates/falak-contracts/src/driver.rs` and implemented by runtime driver crates:
* `falak-driver-sqlite` (Dev2)
* `falak-driver-postgres` (Dev2)
* `falak-driver-d1` (Dev3)

```rust
pub trait StorageDriver {
    type Tx: Transaction;

    /// Return the static capability profile of this driver.
    fn profile(&self) -> &CapabilityProfile;

    /// Execute a single read statement outside an explicit transaction block.
    async fn query(&self, ctx: &RequestContext, statement: Statement) -> Result<Rows>;

    /// Execute a sequence of statements atomically (all succeed or all rollback).
    /// Guaranteed on all compliant drivers.
    async fn batch(&self, ctx: &RequestContext, statements: Vec<Statement>) -> Result<Vec<Outcome>>;

    /// Begin an interactive transaction. Fails with ErrorKind::Unsupported if
    /// the driver lacks the `interactive_transactions` capability.
    async fn begin(&self, ctx: &RequestContext, options: TxOptions) -> Result<Self::Tx>;
}

pub trait Transaction {
    async fn query(&mut self, statement: Statement) -> Result<Rows>;
    async fn execute(&mut self, statement: Statement) -> Result<Outcome>;
    async fn commit(self) -> Result<()>;
    async fn rollback(self) -> Result<()>;
}
```

## 3. Capabilities Taxonomy

The 14 capabilities declared in `crates/falak-contracts/src/capability.rs` (ARCHITECTURE §4.4) are categorized into transactions, concurrency, and engine features.

### 3.1 Transactions
* `interactive_transactions`: Allows arbitrary queries and executions interleaved with application logic within an open transaction block (`BEGIN` ... `COMMIT`/`ROLLBACK`).
* `atomic_batch`: Allows atomic execution of a pre-compiled list of statements in a single round-trip or transaction without client round-trips.
* `savepoints`: Allows nested transaction boundaries via `SAVEPOINT <name>`, `RELEASE SAVEPOINT`, and `ROLLBACK TO SAVEPOINT`.
* `serializable_isolation`: Allows true serializable isolation (`SERIALIZABLE`), guaranteeing conflict-serializable transaction execution (e.g., SSI in PostgreSQL or single-writer exclusive locks in SQLite).

### 3.2 Concurrency
* `concurrent_writers`: Database engine allows multiple non-conflicting write transactions to progress simultaneously without global write-lock serialization.
* `row_level_locking`: Granular row locking constructs such as `SELECT ... FOR UPDATE` or `FOR SHARE`.
* `advisory_locks`: Application-level, non-data locking primitives (e.g. `pg_advisory_xact_lock` or mutex-backed application tables) used for distributed migrations and leader election.
* `read_replicas`: Native driver routing or protocol support for delegating read queries to replica nodes with consistency controls (e.g., Cloudflare D1 Sessions API).

### 3.3 Features
* `native_rls`: Kernel/database-enforced Row Level Security (e.g., PostgreSQL `CREATE POLICY` with forced RLS).
* `returning`: DML clauses that return modified or inserted row representations (`INSERT ... RETURNING`, `UPDATE ... RETURNING`, `DELETE ... RETURNING`).
* `upsert`: Atomic conflict resolution clauses (`ON CONFLICT (...) DO UPDATE` or `DO NOTHING`).
* `json_operators`: Native operators and indexing for querying, extracting, and indexing structured JSON documents (`->`, `->>`, `json_extract`).
* `full_text_search`: Native text indexing, tokenization, and search matching (PostgreSQL `tsvector`/`tsquery`, SQLite FTS5).
* `vector_search`: Native vector embedding indexing and approximate nearest-neighbor search (`pgvector`, `sqlite-vec`).

### 3.4 Numeric Limits
* `max_bound_params`: Maximum number of parameters that can be bound to a single SQL statement.
* `max_statement_bytes`: Maximum allowed size of the raw SQL statement string in bytes.
* `max_row_bytes`: Maximum allowed size for an individual row or column value (e.g. text/blob).
* `max_database_bytes`: Total storage limit enforced per database instance.

## 5. Driver Profiles

### 5.1 SQLite Driver (`falak-driver-sqlite`)

* **Target Environment:** Local native development, embedded appliances, edge micro-VMs, single-binary applications.
* **Underlying Engine:** Modern SQLite (3.45+) accessed via `sqlx` with synchronous WAL mode.
* **Connection Architecture:**
  * Single dedicated writer connection to avoid SQLite database lock contention.
  * Reader pool of concurrent read-only connections (`PRAGMA query_only = ON`).
  * Connection settings:
    * `PRAGMA journal_mode = WAL;`
    * `PRAGMA synchronous = NORMAL;`
    * `PRAGMA busy_timeout = 5000;` (5 seconds timeout before returning `SQLITE_BUSY`)
    * `PRAGMA foreign_keys = ON;`
* **Capability Values & Rationale:**
  * `interactive_transactions`: **Provided**. SQLite supports `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`.
  * `atomic_batch`: **Provided**. Handled inside an immediate transaction.
  * `savepoints`: **Provided**. SQLite natively supports `SAVEPOINT <name>`.
  * `serializable_isolation`: **Provided**. Under WAL mode with `BEGIN IMMEDIATE`, transactions are strictly serialized across writers; readers observe snapshot isolation.
  * `concurrent_writers`: **Not Provided**. SQLite is fundamentally a single-writer database at the file lock level.
  * `row_level_locking`: **Not Provided**. Locking is table/database level.
  * `advisory_locks`: **Provided (Emulated)**. Implemented via an internal single-row lock table (`_falak_advisory_locks`) within an immediate transaction or process-level mutex.
  * `read_replicas`: **Not Provided** in native standalone mode (Litestream acts asynchronously, not as a live query replica).
  * `native_rls`: **Not Provided**. Security and tenant isolation are enforced by the Falak policy engine injecting SQL predicates and generating policy-filtered views.
  * `returning`: **Provided**. Supported via SQLite 3.35+ `RETURNING` syntax.
  * `upsert`: **Provided**. Supported via `ON CONFLICT (...) DO UPDATE / DO NOTHING`.
  * `json_operators`: **Provided**. Supported via built-in `json_extract()`, `->`, and `->>` operators.
  * `full_text_search`: **Provided**. Supported via built-in FTS5 module.
  * `vector_search`: **Not Provided** in core v1 (deferred).
* **Limits:**
  * `max_bound_params`: `32,766` (`SQLITE_MAX_VARIABLE_NUMBER` in SQLite >= 3.32).
  * `max_statement_bytes`: `1,000,000` bytes (`SQLITE_MAX_SQL_LENGTH` default).
  * `max_row_bytes`: `1,000,000,000` bytes (`SQLITE_MAX_LENGTH` default).
  * `max_database_bytes`: `None` (practical file system limit, SQLite architectural limit is 281 TB).

### 5.2 PostgreSQL Driver (`falak-driver-postgres`)

* **Target Environment:** Multi-tenant production servers, cloud hosting (Coolify, Kubernetes, managed RDS/Cloud SQL).
* **Underlying Engine:** PostgreSQL 15+ accessed via `sqlx` connection pool.
* **Connection Architecture:**
  * Dynamically sized connection pool.
  * Each incoming HTTP request leases one connection and executes within a discrete transaction block.
  * Automatic session variable initialization for Row-Level Security:
    `SELECT set_config('falak.tenant_id', $1, true), set_config('falak.subject', $2, true);`
* **Capability Values & Rationale:**
  * `interactive_transactions`: **Provided**. Standard PostgreSQL transaction blocks (`BEGIN`, `COMMIT`, `ROLLBACK`).
  * `atomic_batch`: **Provided**. Multiple statements executed within a single transaction block.
  * `savepoints`: **Provided**. `SAVEPOINT`, `RELEASE SAVEPOINT`, `ROLLBACK TO SAVEPOINT`.
  * `serializable_isolation`: **Provided**. True Serializable Snapshot Isolation (SSI) via `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`.
  * `concurrent_writers`: **Provided**. Multi-Version Concurrency Control (MVCC) enables concurrent, non-conflicting row updates.
  * `row_level_locking`: **Provided**. Full support for `SELECT ... FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` with `NOWAIT` and `SKIP LOCKED`.
  * `advisory_locks`: **Provided**. Native 64-bit and pair 32-bit application locks (`pg_advisory_xact_lock()`, `pg_advisory_lock()`).
  * `read_replicas`: **Provided**. Capable of splitting read queries to read replicas using connection pool routing.
  * `native_rls`: **Provided**. Native `ALTER TABLE ... FORCE ROW LEVEL SECURITY` with `CREATE POLICY ... USING (...) WITH CHECK (...)`.
  * `returning`: **Provided**. Comprehensive `RETURNING` clause across all DML operations.
  * `upsert`: **Provided**. `INSERT ... ON CONFLICT (...) DO UPDATE / DO NOTHING`.
  * `json_operators`: **Provided**. Full JSONB indexing and operator support (`->`, `->>`, `@>`, `?`, `jsonb_path_query`).
  * `full_text_search`: **Provided**. Native `tsvector`, `tsquery`, GIN indexes, and ranking functions.
  * `vector_search`: **Not Provided** in core v1 (extensible via `pgvector` in later phases).
* **Limits:**
  * `max_bound_params`: `65,535` (16-bit unsigned integer limit in PostgreSQL wire protocol).
  * `max_statement_bytes`: `None` (practical limit is 1 GB query string allocation; Falak enforces application-level limit of 10 MB).
  * `max_row_bytes`: `1,073,741,824` bytes (1 GB TOAST maximum column size).
  * `max_database_bytes`: `None` (bounded only by underlying disk capacity).

### 5.3 Cloudflare D1 Driver (`falak-driver-d1`)

* **Target Environment:** Cloudflare Workers edge runtime (`wasm32-unknown-unknown`).
* **Underlying Engine:** Cloudflare D1 (SQLite dialect over Cloudflare distributed storage).
* **Reference Sources:** Checked and verified against Cloudflare documentation on 2026-11-15 (see `specifications/CLOUDFLARE_LIMITS.md`).
* **Capability Values & Rationale:**
  * `interactive_transactions`: **Not Provided**. D1 runs in auto-commit mode and does not allow open transaction handles across async Workers event loop turns.
  * `atomic_batch`: **Provided**. D1 provides `db.batch([stmt1, stmt2, ...])` which executes all statements sequentially in a single SQL transaction. If any statement fails, the entire batch rolls back.
  * `savepoints`: **Not Provided**. Not exposed through the D1 Workers API.
  * `serializable_isolation`: **Not Provided**. D1 executes one writer thread per database with auto-commit or atomic batches, but lacks interactive serializable conflict detection.
  * `concurrent_writers`: **Not Provided**. D1 processes one query/batch at a time per database on a single writer thread.
  * `row_level_locking`: **Not Provided**.
  * `advisory_locks`: **Not Provided**.
  * `read_replicas`: **Provided (Sessions API)**. Supports global read replication using `withSession` and sequential consistency tokens (`getBookmark()`).
  * `native_rls`: **Not Provided**. Policy engine injects SQL predicates or generates policy-filtered views.
  * `returning`: **Provided**. SQLite `RETURNING` is supported.
  * `upsert`: **Provided**. SQLite `ON CONFLICT` is supported.
  * `json_operators`: **Provided**. SQLite `json_extract()` and `->` / `->>` operators supported.
  * `full_text_search`: **Provided**. SQLite FTS5 module is supported.
  * `vector_search`: **Not Provided**.
* **Limits (Vendor Verified):**
  * `max_bound_params`: **`100`** (strictly enforced per query; exceeds fail with error).
  * `max_statement_bytes`: **`100,000`** bytes (~97.6 KB).
  * `max_row_bytes`: **`2,000,000`** bytes (2 MB max row, string, or BLOB).
  * `max_database_bytes`: **`10,737,418,240`** bytes (10 GB on Workers Paid; 500 MB on Free).
  * `max_query_result_size`: **`50 MB`** (per query result set).
  * `max_query_duration`: **`30 seconds`** (bounds a single query or batch call).
  * `max_queries_per_invocation`: **`1,000`** on Paid (`50` on Free).

## 6. Execution & Concurrency Contracts

### 6.1 Transaction Lifecycle
1. **Interactive Transactions (SQLite & PostgreSQL):**
   * Initiated via `StorageDriver::begin(&ctx, options)`.
   * For PostgreSQL, the connection automatically applies session configuration:
     ```sql
     SET LOCAL falak.tenant_id = '<tenant>';
     SET LOCAL falak.subject = '<subject>';
     ```
   * If a transaction is dropped without explicit `commit()`, the driver's `Drop` implementation triggers an asynchronous rollback to return the connection cleanly to the pool.
2. **Atomic Batches (All Drivers):**
   * Implemented on SQLite via `BEGIN IMMEDIATE; ... COMMIT;`.
   * Implemented on PostgreSQL via a single multi-statement block or single `BEGIN ... COMMIT`.
   * Implemented on D1 via `D1Database::batch()`.

### 6.2 The Read-Then-Write Contract (Optimistic Batching)
Because Cloudflare D1 does not support interactive transactions, commands that perform a read followed by a conditional write cannot hold a read lock across turns.
The compiler compiles such commands into a **conditional atomic batch** guarded by an optimistic concurrency `version` column:
```sql
UPDATE notes 
SET title = ?2, body = ?3, version = version + 1, updated_at = ?4
WHERE id = ?1 AND version = ?5;
```
* If `rows_affected == 0`, the driver detects that the record was modified concurrently and rolls back the batch, returning `ErrorKind::PreconditionFailed` (HTTP 412) or `ErrorKind::Conflict` (HTTP 409).
* Applications requiring complex multi-entity interactive transactions must declare `requires: [interactive_transactions]` in `app.yaml`. The Falak compiler rejects deployment of such apps to Cloudflare D1 at build time.

### 6.3 Retry and Error Classification Contract
Storage drivers must classify low-level database errors into Falak's standard `ErrorKind` taxonomy (`crates/falak-contracts/src/error.rs`):

| Database Error Condition | SQLite Error | PostgreSQL SQLSTATE | Falak ErrorKind | Retryable? |
| :--- | :--- | :--- | :--- | :--- |
| Lock contention / busy | `SQLITE_BUSY`, `SQLITE_LOCKED` | `55P03` (`lock_not_available`) | `ErrorKind::Unavailable` | **Yes** (Exponential backoff) |
| Deadlock detected | `SQLITE_BUSY` | `40P01` (`deadlock_detected`) | `ErrorKind::Conflict` | **Yes** (Immediate retry) |
| Serialization failure | `SQLITE_BUSY_SNAPSHOT` | `40001` (`serialization_failure`) | `ErrorKind::Conflict` | **Yes** (Immediate retry) |
| Query timeout | `SQLITE_INTERRUPT` | `57014` (`query_canceled`) | `ErrorKind::Timeout` | **Yes** (Subject to budget) |
| Unique constraint | `SQLITE_CONSTRAINT_UNIQUE` | `23505` (`unique_violation`) | `ErrorKind::Conflict` | **No** |
| Foreign key constraint | `SQLITE_CONSTRAINT_FOREIGNKEY`| `23503` (`foreign_key_violation`) | `ErrorKind::InvalidInput` | **No** |
| Check constraint | `SQLITE_CONSTRAINT_CHECK` | `23514` (`check_violation`) | `ErrorKind::InvalidInput` | **No** |
| Value out of range | `SQLITE_TOOBIG` | `22003` (`numeric_value_out_of_range`)| `ErrorKind::InvalidInput` | **No** |

#### Retry Policy:
* **Max attempts:** 3 attempts.
* **Backoff formula:** Full jitter: $t = \text{random}(0, \min(M, B \times 2^{\text{attempt}}))$ where initial base $B = 10\,\text{ms}$, cap $M = 250\,\text{ms}$.
* Total retry budget per request must not exceed $500\,\text{ms}$.

## 7. Migration & DDL Contracts

1. **Transactional DDL:**
   * **PostgreSQL:** Fully transactional. Table creations, alterations, and index creations (except `CONCURRENTLY`) roll back on failure.
   * **SQLite:** DDL is partially transactional within an immediate transaction.
   * **D1:** DDL is executed via batch. Table rebuilds require `PRAGMA defer_foreign_keys = on;` to migrate relationships cleanly without cascade drops.
2. **Migration Concurrency Control:**
   * **PostgreSQL:** Employs transactional advisory locks:
     `SELECT pg_advisory_xact_lock(hashtext('falak_migration_lock'));`
   * **SQLite:** Employs single-writer lock via `BEGIN IMMEDIATE` on `_falak_migrations`.
   * **D1:** Acquires a lock row with lease timeout in `_falak_migrations_lock`.
3. **Drift Detection:**
   * Every applied migration stores its checksum (SHA-256) in `_falak_migrations`. Any discrepancy between compiled IR migrations and database history causes `falak migrate` to abort with a drift error.

## 8. T0.8 Spike Result (2026-11-15)

Crate: `crates/falak-spike-t08` (throwaway). One hard-coded entity, `notes`, served at `GET /notes/{id}`.

* **Workers:** `https://falak-spike-t08.falakme.workers.dev/notes/1`, reading a D1 database in the Falak Cloudflare account.
* **Native:** `cargo run -p falak-spike-t08 --bin native -- /notes/1`, reading in-memory SQLite.
* **Result:** both return the identical body `{"id":1,"title":"hello","body":"same row on D1 and SQLite"}`. An unknown id returns 404 on Workers.
* **WASM size:** 238,112 bytes after `wasm-opt` (release, `opt-level = "z"`, LTO). Upload to Workers: 271 KiB, 82 KiB gzip. Worker startup 2 ms. This includes the `worker` crate, `serde_json` and the JS glue, so it is the floor for the runtime, not the full cost.
* **What it did not test:** `falak-driver-d1` (the spike calls the binding directly), batches, error mapping, or load.
* **Design change forced:** none. The same SQL text and the same JSON function ran on both. D1 integer ids come back as JSON numbers, so ids stay below 2^53.
